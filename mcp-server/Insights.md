## 2026-09-26 — [Mistake] A `"zod/*"` tsconfig path mapping copied from `reviewer-core/` hijacks the MCP SDK's own `zod/v3` subpath resolution
`tsconfig.json`'s `paths` originally copied `reviewer-core/tsconfig.json`'s `"zod": ["./node_modules/zod"]` **and** `"zod/*": ["./node_modules/zod/*"]` verbatim. `server/src/vendor/shared` only ever does `import { z } from 'zod'` (the bare specifier), so the `zod` mapping is needed to force the shared sources to type-check against this package's own zod install rather than `server/node_modules`. But `@modelcontextprotocol/sdk`'s own `.d.ts` files do `import type * as z3 from 'zod/v3'` internally, and the `"zod/*"` wildcard mapping intercepts that subpath import too, rewriting it to `./node_modules/zod/v3` in a way that stops matching the SDK's expected type shape. The visible symptom was `registerTool`'s `AnySchema` rejecting perfectly normal optional Zod fields (`TS2345`, and in one case `TS2589` "type instantiation is excessively deep") with no error pointing at the actual cause. Fix: drop the `"zod/*"` wildcard entry and keep only the bare `"zod"` mapping — `vendor/shared` never imports a `zod` subpath, so nothing in this package's own code needs it, and removing it stops shadowing the SDK's internal resolution.

## 2026-09-26 — [Mistake] `ToolResult` needed an index signature to satisfy the MCP SDK's `CallToolResult`
The handwritten `ToolResult` type in `src/domain/tool-result.ts` (`{ content: [...]; isError?: boolean }`) is structurally what `ok()`/`fail()` return, but TypeScript rejected assigning it to the SDK's `CallToolResult` return type on `registerTool`'s handler. The SDK's `CallToolResult` (like other MCP result types) carries `[key: string]: unknown` so clients can round-trip arbitrary extra top-level fields per the spec; a type without that index signature isn't assignable to one that has it, even when every named field matches. Fix: add `[key: string]: unknown;` to `ToolResult` itself, rather than casting at each call site.

## 2026-09-26 — [Context] Claude Code's per-server `mcp.json` `"timeout"` field and the `MCP_TOOL_TIMEOUT`/`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` env vars, verified against the installed CLI (2.1.283)
Confirmed by inspecting the installed `claude` binary directly (`strings` on `~/.local/share/claude/versions/2.1.283`), not just the public docs already cited in the plan (§0.4): the effective per-call timeout is `Math.min(Math.max(config.timeout ?? env.MCP_TOOL_TIMEOUT ?? 1e8, 1000), <idle-timeout-derived cap>)` — i.e. a server's `mcp.json` `"timeout"` (ms) overrides `MCP_TOOL_TIMEOUT` for that server only, values below 1000ms are ignored, and it is a hard wall-clock limit: progress notifications never extend it (the SDK-facing description string embedded in the binary reads verbatim "Hard wall-clock limit per call; progress notifications do not extend it."). Separately, `MCP_TOOL_TIMEOUT`'s own default is `1e8` ms (~28h), and the **idle** timeout (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`, reset by progress notifications, unlike the hard timeout) defaults to 1,800,000ms (30 min) for `stdio` servers specifically — other transport types (`sse-ide`, `ws-ide`, `sdk`) disable the idle timeout entirely. `claude --mcp-config <file>` (space-separated list of JSON files or strings) and `claude mcp add --scope local -e KEY=value <name> -- <command>` both exist as documented in `claude --help` / `claude mcp add --help` on this install — no deviation from the plan's §0.4/§13 assumptions.

## 2026-09-26 — [Context] ESLint flat config: a later config block matching the same files fully replaces (not merges) an earlier block's value for the same rule
While splitting the onion-layering `no-restricted-imports` override into a `src/domain/**` block and a separate `src/tools/**` block (security/architecture review fixes), discovered that flat config doesn't accumulate array-valued rule options across multiple matching config objects — if two objects in `eslint.config.mjs` both match a file and both set `@typescript-eslint/no-restricted-imports`, the *later* object's full options (its whole `paths`/`patterns` array) win for that file, they don't concatenate with the earlier one's. Fix: each per-folder override block (`src/domain/**/*.ts`, `src/tools/**/*.ts`) now repeats every restriction that folder needs (the shared `@devdigest/shared`/`**/api/*` rules plus its own folder-specific one) instead of relying on an earlier shared block to supply part of it — confirmed by adding a throwaway violating file per rule and checking `npm run lint` actually flags it before deleting the file.

## 2026-09-26 — [Context] `fetch`'s `redirect: 'error'` surfaces a redirect as a rejected `TypeError` whose message names "redirect", not as a 3xx `Response`
Setting `redirect: 'error'` on a `fetch` call (added to `src/api/client.ts` so a misconfigured `DEVDIGEST_API_URL` can't silently follow a redirect off loopback, security review M3) makes a real 3xx response reject the promise with a `TypeError` rather than resolving to a `Response` with `status` in the 300s — so it lands in the same `catch` block as a connection failure and must be distinguished by message content (`/redirect/i.test(err.message)`) before falling back to the generic `'unreachable'` mapping. `httpErrorFromResponse` (`src/api/errors.ts`) still special-cases a 3xx `Response` defensively (checked first, before parsing any body) for any fetch implementation — including this package's own hermetic fake in `test/helpers/fake-api.ts` — that resolves a redirect response instead of rejecting it.

## 2026-09-27 — [Mistake] `formatBlast`'s char budget forgot the `\n` that `ok()` inserts between the summary line and the JSON payload
`domain/format.ts`'s `formatBlast` computed `budget = MAX_RESPONSE_CHARS - summary.length` and truncated `downstream`/`changed_symbols` until `JSON.stringify(payload).length <= budget` — but `tool-result.ts`'s `ok(summaryLine, payload)` renders `` `${summaryLine}\n${JSON.stringify(payload)}` ``, so the actual rendered text is one character longer than `summary.length + JSON.stringify(payload).length`. A payload sized to exactly fill the old budget pushed the combined tool output one char past `MAX_RESPONSE_CHARS`. Fixed by budgeting `MAX_RESPONSE_CHARS - summary.length - 1`. `formatReview`/`formatConventions`/`formatAgents` don't have this bug because their shared `PAYLOAD_BUDGET` already reserves a flat `SUMMARY_MARGIN` (500 chars) well above 1 — only `formatBlast`'s deliberately tighter per-call budget (chosen because the degraded-suffix summary line varies in length) was exact enough for the missing `+1` to matter. Any future formatter that computes its own tight `MAX_RESPONSE_CHARS - summary.length`-style budget (instead of reusing the shared margin constant) needs to account for `ok()`'s joining `\n` explicitly.

## 2026-09-27 — [Context] Extending `DevDigestApi` (`domain/ports.ts`) breaks any test file with its own hand-rolled fake object typed directly as `DevDigestApi`, even outside the task that owns the interface
Adding `getBlast(prId): Promise<BlastLite>` to `DevDigestApi` (T6, blast-radius plan) broke `tsc --noEmit` in `test/domain-resolve.test.ts`, a file not in that task's owned paths — its local `fakeApi(overrides): DevDigestApi` helper (`test/domain-resolve.test.ts:20-31`) returns an object literal typed directly as `DevDigestApi`, so TypeScript's structural check requires every property, including a brand-new one, before the object is assignable. `test/domain-wait.test.ts`'s fakes (`{ listRuns } as unknown as DevDigestApi`) were unaffected, because the `as unknown as` cast bypasses structural checking entirely. Fixed with a one-line, mechanical addition (`getBlast: vi.fn(),`) to the unaffected file — not a functional change, just keeping an interface-conforming fixture in sync. When a plan's Owned paths list a port/interface file but not every file that implements it as a literal (vs. an `as unknown as` cast), expect this ripple and grep for other `: DevDigestApi` (or the equivalent port type) object-literal return types before declaring typecheck done.

## 2026-09-28 — [Decision] Root `/.mcp.json` replaces `mcp-server/mcp.json` outright, rather than keeping both
Mentor review on PR #4 pointed out the package was only reachable via `claude mcp add --scope local` or an explicit `claude --mcp-config mcp-server/mcp.json`, so a fresh clone got nothing until someone ran one of those by hand. Added `/.mcp.json` at the repo root (identical contents — `devdigest`, stdio, `mcp-server/bin/start.sh`, `DEVDIGEST_API_URL` default, `timeout: 300000`) so Claude Code auto-loads it every session. Rather than keep `mcp-server/mcp.json` alongside it for the `--mcp-config`/isolation use case, deleted it: two files registering the same `devdigest` server name is exactly the "duplicate-registration confusion" a reviewer would flag next, and nothing else depended on the file (`npm run inspect` invokes `bin/start.sh` directly, `mcp-server/package.json`'s scripts never reference `mcp.json`, and no CI workflow does either — confirmed via `grep -rn "mcp.json"` across non-`docs/plans` files before deleting). `docs/plans/2026-09-26-mcp-server.md`'s own "no root `.mcp.json`" language (§T6) reflected a real, deliberate decision at the time (T6, 2026-09-26) — this is a superseding decision, not a mistake in that plan; the plan file itself is left untouched as a historical record, per the "don't edit history" convention.

## 2026-09-28 — [Decision] `get_findings` without `run_id` returns one review per agent, not one ambiguous "latest" review
Mentor review on PR #4: the old no-`run_id` branch (`tools/get-findings.ts`) picked a single review by `created_at desc` across *every* agent's reviews combined — with two agents having reviewed a PR, the model only ever saw whichever agent happened to run most recently, with no way to learn a second agent had even reviewed it. Fixed by grouping candidates (`kind === 'review'`, optionally pre-filtered by `agent`) to one *latest* review per agent (keyed by `agent_id ?? agent_name ?? id`), then shaping them with a new `formatFindingsList` (`domain/format.ts`) into `{ repo, pr, total_findings, counts, reviews: [...] }`. Chose to sort `reviews` by (filtered) CRITICAL count desc, then WARNING, then SUGGESTION, then agent name — not by `created_at` or alphabetically — so the agent with the most serious findings leads regardless of run order; tested explicitly in `domain-format.test.ts` and `get-findings.test.ts` with a case where the alphabetically-first agent has the fewest findings, to prove severity (not name) drives the order. The `run_id` branch was deliberately left untouched (still single-review `formatReview`, shared with `run_agent_on_pr`) rather than wrapped in a `reviews:[...]` envelope for "consistency" — a `run_id` already names one specific run unambiguously, so a list shape there would only add a needless `.reviews[0]` indirection for callers and risk changing `run_agent_on_pr`'s shape by association (it shares `formatReview` with this branch).
