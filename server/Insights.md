## 2026-09-18 — [Context] Agent-run cost was already computed, just never persisted
Before the "agent run cost" feature (branch `feat/agent-run-cost`), reviewer-core's `reviewPullRequest()` already returned `ReviewOutcome.costUsd` (real cost from OpenRouter's `usage.cost` extension, falling back to `PriceBook`/`estimateCost`), and the OpenAI/Anthropic adapters (`server/src/adapters/llm/openai.ts`, `anthropic.ts`) already computed `costUsd` via `estimateCost()`. It was silently dropped in `server/src/modules/reviews/run-executor.ts:213` (`const { tokensIn, tokensOut, grounding } = outcome;` never destructured `costUsd`) before reaching `completeAgentRun()` — `agent_runs` had no `cost_usd` column at all. When a request says "add cost tracking," check whether the value is already computed upstream and just needs plumbing through persistence + contracts + UI, rather than assuming new cost math is needed. Also: `server/src/vendor/shared/contracts/observability.ts` already had `cost_usd`/`total_cost_usd`/`avg_cost_usd` fields for the separate Multi-Agent Review feature (`AgentColumn`, `MultiAgentRun`, `AgentStats`) — unimplemented, but they set the field-naming convention (`cost_usd`, nullable) that new `RunStats`/`RunSummary`/`PrMeta` fields should match for consistency.

## 2026-09-18 — [Context] `repository.ts`'s method param types are copy-pasted, not imported, from `run.repo.ts`
`server/src/modules/reviews/repository.ts`'s `completeAgentRun()` wrapper re-declares its own inline parameter type instead of importing it from `server/src/modules/reviews/repository/run.repo.ts`. Adding a field to `run.repo.ts`'s `completeAgentRun` signature (e.g. `costUsd`) requires a matching manual edit in `repository.ts` too, or the call site in `run-executor.ts` fails to typecheck with an "object literal may only specify known properties" error that points at the call site, not the actual mismatched type in `repository.ts`.

## 2026-09-18 — [Context] `server/src/vendor/shared` and `client/src/vendor/shared` are hand-mirrored, not a single source of truth
Both packages vendor their own copy of the same Zod contracts (e.g. `contracts/trace.ts`, `contracts/platform.ts`). Every contract change (e.g. adding `cost_usd` to `RunStats`/`RunSummary`/`PrMeta`) must be applied identically to both files by hand — TypeScript won't catch a missed side since they're structurally separate packages, not a shared import. Diff the two files after any shared-contract edit to confirm they match.

## 2026-09-18 — [Pattern] `pulls/status.ts` already had pre-built, tested findings-tally scaffolding — reuse it, don't re-count
Before the FINDINGS-column feature (branch `feat/agent-run-cost`), `server/src/modules/pulls/status.ts:23` already exported `rollupSeverities(rows: {severity:string}[])`, unit-tested in `server/test/pulls-status.test.ts:52-67`, whose own doc comment (`status.ts:6-10`) explicitly says the PR list should show "a FINDINGS severity breakdown" — pre-built for exactly this feature but never wired into `pulls/routes.ts`. Reused it in the `GET /repos/:id/pulls` handler instead of writing a new tally loop. One catch: it returns lowercase keys (`{critical, warning, suggestion}`), while every other severity-shaped value in the app (the `Severity` Zod enum, `FindingRecord.severity`, the client's `SeverityBadge`/`SEV` map) uses uppercase `CRITICAL`/`WARNING`/`SUGGESTION`. Kept `rollupSeverities` as-is (it's tested) and mapped its lowercase output to uppercase at the call site (`routes.ts`) for the wire contract, rather than changing the helper or introducing a second casing convention on the wire.

## 2026-09-24 — [Mistake] `reviews.it.test.ts` is not hermetic once a module under test calls `container.llm('openrouter')`/`container.github()` without an override — `LocalSecretsProvider` silently falls through to the real local `.env`
`LocalSecretsProvider.get()` (`src/adapters/secrets/local.ts:37-42`) checks the JSON secrets store first, then falls back to `this.env[key]` (real `process.env`, populated from `server/.env` via `dotenv/config` in `config.ts:1`) when the store has no override. `server/test/reviews.it.test.ts`'s `appWith()` (`:113-125`) only overrides `overrides.llm.openai`/`.anthropic` and never sets `overrides.secrets` — before T6 this was harmless (nothing in the request path touched `openrouter`/`github`), but once `run-executor.ts` started constructing `IntentClassifier` unconditionally and calling `ensureIntent` on every `executeRuns`, every review-triggering test in that file started resolving a REAL `OpenRouterProvider`/`OctokitGitHubClient` from whatever real key happens to sit in this machine's `server/.env`/`~/.devdigest/secrets.json` — confirmed live on this machine (a real-looking `OPENROUTER_API_KEY` + `GITHUB_TOKEN` in `server/.env`, gitignored but present locally) by the fact that every review test in that file takes ~8000-8500ms, matching `ENSURE_INTENT_TIMEOUT_MS` almost exactly (a `ConfigError` from a genuinely-missing key resolves near-instantly instead). `server/test/intent.it.test.ts` (written after T6, in the same session) gets this right — its `appWith()` always sets `secrets: new MockSecretsProvider({})` specifically so a missing `llm.openrouter` override degrades deterministically instead of silently reaching a real network call. Any `.it.test.ts` `appWith`/`buildApp` helper that doesn't override `secrets` should be treated as a latent non-hermeticity risk the moment a new code path adds a container port call (`llm`, `github`, `embedder`) that the helper didn't anticipate — not just at the point the helper was first written.

## 2026-09-24 — [Context] `pr_files` has no ordering column, so no server layer can promise "PR order"
`server/src/db/schema/pulls.ts:47-60`'s `prFiles` table has only a random-uuid PK, no sequence/position column, and `PullsRepository.getPrFiles` (`pulls/repository.ts:121-123`) has no `ORDER BY` — so its return order is whatever Postgres's heap scan happens to produce, not insertion order. The Smart Diff feature (`smart-diff/repository.ts`'s `getPrFiles`) deliberately makes no ordering promise either, and `smart-diff/helpers.ts`'s `buildSmartDiff` only preserves *input* order within a role bucket — it does not re-derive "PR order". The actual "original order" guarantee comes from the client: `pr.files` (the array the `GET /pulls/:id` GitHub sync already writes via `replacePrFiles`, `pulls/repository.ts:130-143`, in GitHub's own file order) is the one ordering source of truth, and `DiffTab/helpers.ts`'s `resolveSmartGroups` explicitly re-sorts each Smart Diff group's files by their index in that array rather than trusting the server's bucket order. Any future feature that needs a stable "PR file order" should sort against the client's `pr.files` (or add a real ordering column) rather than assuming `pr_files` rows come back in insertion order.

## 2026-09-27 — [Mistake] `POST /repos/:id/resync` always returned 202 even for a repo with no clone, because the failure only surfaced inside an async job that persists nothing
`repo-intel/routes.ts`'s resync handler enqueued a `RESYNC_JOB_KIND` job unconditionally and always replied 202 (comment: "202 even when enqueue fails … so the UI can still poll /index-state"). The job handler, `RepoIntelService.resyncRepo` (`service.ts:143-148`), degrades to `{status:'degraded', reason:'no_clone'}` in ~10ms when `repo.clonePath` is null — but that return value is only consumed by `registerIndexJobHandlers`'s wrapper, which discards it (JobRunner expects `Promise<void>`), and nothing gets written to `repo_index_state`. Net effect: the job finishes near-instantly and "successfully" from the job table's point of view, but the one signal the client polls (`GET /repos/:id/index-state`'s `updatedAt`/`lastIndexedSha`) never advances — the client (`useBlastResync.ts`) has no way to distinguish "resync is genuinely still running" from "resync silently did nothing" and just polls until its own client-side timeout. Fixed by adding `RepoIntelService.assertResyncable(repoId)` (throws `NotFoundError`/a new `ConflictError` — `platform/errors.ts` — for an unknown repo / no clone respectively) and calling it from the route *before* enqueueing, so the failure is synchronous and visible instead of buried inside a fire-and-forget job. General lesson: when a route enqueues a background job and always returns 202 "so the UI can keep polling," check whether the job's failure paths actually produce an observable state change — a job that returns early without persisting anything is indistinguishable, from the poller's perspective, from one that's still working.

## 2026-09-27 — [Decision] "Is this file known to the index?" reads `file_rank`, not `symbols`
Blast's `files.indexed` count (`repo-intel/repository.ts`'s `countIndexedFiles`) deliberately checks `file_rank`, not `symbols`. `pipeline/rank.ts`'s `computeFileRank(walk.files, edgeRows)` (called from `pipeline/full.ts:228`) writes exactly one `file_rank` row per file the full-index walk actually processed, regardless of whether that file declared any symbol. `symbols`, by contrast, only gets rows for files with ≥1 parsed declaration (`pipeline/full.ts`'s parse phase only pushes to `symbolsBuf` when `parseSymbols` finds something) — so a file with zero declarations (a pure re-export, a types-only barrel, a constants file with no functions/classes) is "indexed" but would read as "not indexed" if counted via `symbols.path`. Also relevant: `file_rank` is populated only when the T3 graph/rank block runs (skipped entirely when the soft time budget trips mid-index, `pipeline/full.ts`'s `softBudgetReached`), so on a `partial` index some genuinely-parsed files can still be absent from `file_rank` — an accepted approximation, not a bug, since `partial` already means "incomplete" to the caller. General lesson: when a feature needs "does the index know about file X", check which pipeline step writes one row *per walked file* unconditionally vs. one row *per successful parse result* — they diverge exactly on files with no symbols.

## 2026-09-27 — [Context] A PR's `pr_files` rows don't exist until its detail page (`GET /pulls/:id`) has been opened at least once
Verified live against the dev API (`GrinIara/dev-digest`'s seeded PR #218): `GET /pulls/:id/blast` initially returned `files.changed: 0` and `degraded: true, reason: 'no_data'` even though the repo's index was `full` — not because the index was stale, but because `pr_files` was empty for that PR until `GET /pulls/:id` (which calls `replacePrFiles` during its GitHub sync, `pulls/repository.ts:130-143`) had been hit once. Matches the A7 assumption already documented in `docs/plans/2026-09-27-blast-radius.md` ("coverage is sparse, because `pr_files` only exists for PRs whose detail page was opened") — recorded here because it's easy to mistake for an indexing bug when smoke-testing a `pulls/:id/*`-family route against a freshly seeded PR that was never opened in the UI.

## 2026-09-28 — [Mistake] `blast-map.test.ts`'s "self-caller" unit tests exercised a DB state `resolveReferences` can never actually produce
Mentor review on PR #4 flagged `blast/helpers.ts`'s `groupDownstream` for re-filtering self-callers that `repo-intel/repository.ts`'s `getResolvedCallers` (persistent path) already excludes. Verifying this exposed why the original unit tests (`blast-map.test.ts`, now removed) never caught it: they constructed a `BlastResult` by hand with a caller row whose `file` equals its `viaSymbol`'s declaring file — a shape `groupDownstream`'s caller only ever receives from `service.ts`'s `getPersistentBlast`, which in turn only ever gets rows from `getResolvedCallers`'s SQL join on `references.decl_file`. `resolveReferences` (`repository.ts:400-421`) only sets `decl_file` when `file_edges.from_file = r.from_path` has a matching `to_file` whose `symbols` row satisfies `to_symbol` — and a file never has an import edge to itself, so a same-file reference's `decl_file` provably stays `NULL` (never selected by `inArray(declFile, declFiles)`) whenever the DB is populated through the real pipeline. The old integration test (`blast.it.test.ts`, the "reads a full persistent index" case) also bypassed this: it inserted a `references` row with `declFile` hand-set to the same file, instead of going through `resolveReferences`, so it "proved" the app-level filter caught something the real pipeline can't produce in the first place. Fixed by removing the hand-crafted self-reference from that test and adding a new one that seeds `file_edges`/`symbols`/`references` (with `decl_file: null`) and calls `repoIntelRepo.resolveReferences()` for real, asserting the same-file reference's `decl_file` stays `NULL` while a genuine cross-file one resolves. General lesson: a unit test that hand-constructs an intermediate data shape (here, `BlastResult.callers`) to probe an invariant should first check whether the *real* producer of that shape can even generate the case under test — otherwise the test can enshrine a defensive filter for a state that's already structurally unreachable.
