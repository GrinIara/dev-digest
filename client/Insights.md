## 2026-09-18 — [Pattern] No shared number-formatting util — colocate formatters per feature folder, even if similar
`client/src/lib` has no `format.ts`; formatting helpers live colocated in each feature folder's own `helpers.ts`. Precedent: `RunTraceDrawer/helpers.ts`'s `formatTokens` already renders tokens differently ("12k→1.5k") than the PR-list area does. When the "agent run cost" feature needed a `formatCost` in both `pulls/helpers.ts` (list column, timeline) and `RunTraceDrawer/helpers.ts` (stats tile), that precedent was followed by writing `formatCost` twice, colocated, rather than introducing a new shared module — matches the existing convention of "colocated feature logic" over premature cross-cutting abstraction.

## 2026-09-18 — [Mistake] Two independent unused scaffolds for the same "findings by severity" shape used different casing
While building the PR-list FINDINGS column, found `client/src/lib/types.ts:38-48`'s unused `PrRowView.findings: {CRITICAL,WARNING,SUGGESTION}` (uppercase) — a leftover scaffold never wired to any component. Server-side, `server/src/modules/pulls/status.ts` had its own unused scaffold, `rollupSeverities`, returning lowercase `{critical,warning,suggestion}` (see server `Insights.md`). Two different people/sessions apparently pre-built the same concept with inconsistent casing and neither got wired up. Went with uppercase for the real `PrMeta.findings` wire field since it matches the live, load-bearing convention (`Severity` enum values, `FindingRecord.severity`, `SeverityBadge`/`SEV` map in `@devdigest/ui`) — lowercase was the outlier. If you find another unused "scaffold" type in this codebase, check its key casing against `Severity` before trusting it as the contract shape.

## 2026-09-18 — [Context] `@devdigest/ui` never imports `@devdigest/shared` — new UI components take their own minimal prop types
`client/src/vendor/ui` (the design-system package) has zero dependency on `@devdigest/shared`'s contract types anywhere — e.g. `SeverityBadge` (`vendor/ui/primitives/Badge.tsx:52`) takes its own local `Severity` type from `vendor/ui/primitives/tokens.ts:3`, not the shared `Severity` Zod enum; feature code casts at the boundary (`FindingCard.tsx` does `f.severity as Severity`). Followed this when adding `FindingsHoverPopover` (`vendor/ui/kit/FindingsHoverPopover.tsx`): it takes a local `FindingPreview` interface (severity/title/category/file/start_line/confidence/rationale) instead of importing `FindingRecord`, and callers (`PRRow.tsx`, `RunHistory.tsx`) explicitly map `FindingRecord[]` → `FindingPreview[]` at the call site. Don't import `@devdigest/shared` into `vendor/ui` even when the shapes are identical — it's a deliberate architectural boundary (design system has no API-contract dependency).

## 2026-09-18 — [Pattern] Timeline run tiles get their per-run findings by cross-referencing the sibling Review-runs fetch, not a new request
`RunHistory.tsx`'s Timeline only receives `RunSummary[]` (from `usePrRuns` → `GET /pulls/:id/runs`), which carries just a total `findings_count`, no per-severity breakdown or the findings themselves. The Review-runs section on the same tab already fetches `ReviewRecord[]` (each with `run_id` + a full `findings` array) for the very same page. Added a `findingsByRunId: Map<run_id, FindingRecord[]>` built in `FindingsTab.tsx` from that already-fetched `reviews` array, passed down into `RunHistory` as a prop — gives the Timeline severity icons + a hover popover with zero new network requests. When a component on this tab seems to be missing data, check whether a sibling component on the same tab already fetched it before adding a new hook/endpoint.

## 2026-09-19 — [Mistake] A nested `position:absolute` floating panel gets clipped by an `overflow:hidden` ancestor — portal it instead
`FindingsHoverPopover` (`vendor/ui/kit/FindingsHoverPopover.tsx`) originally rendered its panel as a `position:absolute` child nested inside the hovered trigger. Both real call sites sit inside an `overflow:hidden` ancestor — the PR list's `tableCard` (`app/repos/[repoId]/pulls/styles.ts:90`) and the Review-run accordion's rounded card (`ReviewRunAccordion.tsx:67`) — so the panel got silently clipped/invisible instead of floating on top, which unit tests never caught (jsdom doesn't apply CSS clipping, so `screen.findByText(...)` still passed). Fixed by rendering the panel via `createPortal(..., document.body)` with `position:fixed` coordinates computed from the trigger's `getBoundingClientRect()` (`FindingsHoverPopover.tsx:15,60,90`) and a high `zIndex:1000` (`:107`) — a body-level portal can't be clipped or out-stacked by any ancestor, by construction. Also needed a short close-delay (`CLOSE_DELAY_MS`, `:32,72`) so moving the cursor from the trigger into the now-detached-in-the-DOM popover doesn't flicker it shut. When adding any new hover/floating panel in this codebase, check for an `overflow:hidden` ancestor first — if one exists (or might later), portal to `document.body` from the start rather than nesting `position:absolute`.

## 2026-09-24 — [Context] `TraceSection`'s `icon` prop is a closed literal union, not the shared `IconName` type — adding a new trace section can't freely pick an icon without also owning `TraceSection.tsx`
`RunTraceDrawer/_components/TraceSection/TraceSection.tsx:15` types `icon` as `"Settings" | "Gauge" | "FileText" | "Wrench" | "Code" | "AlertOctagon"` (a hand-picked subset of `vendor/ui`'s full `IconName`), not `IconName` itself like every other icon-accepting prop in this codebase (`Badge`, `SectionLabel`, `Chip`, `EmptyState` all take `icon?: IconName`). Adding the intent-layer's classifier-call section (`IntentCallSection.tsx`) needed an icon and the plan's own spec named `"Sparkles"`, which isn't in that union and isn't in `TraceSection.tsx`'s Owned paths for that task — widening the union would've meant editing a file outside scope. Reused `"Gauge"` (already used by the adjacent Stats section) instead of widening the union. When a task's owned paths include a `TraceSection` consumer but not `TraceSection.tsx` itself, check this union first — don't assume any `IconName` value will typecheck.

## 2026-09-24 — [Pattern] A finished review run surfaces via `FindingsTab.onRunDone`, not `useRunReview.onSuccess` — invalidate derived per-PR caches there
`useRunReview.onSuccess` (`lib/hooks/reviews.ts`) fires when the POST to `/pulls/:id/review` *returns*, which is before the agents actually finish (the run streams over SSE afterward) — invalidating there only refreshes state that existed at trigger time. The real "a run just finished" signal is `FindingsTab`'s `onRunDone` callback, wired in `page.tsx` to call `invalidateActiveRuns()`, `invalidateRunHistory()` and `refetchReviews()` — and `invalidateRunHistory` (`hooks/usePrDetailPage.ts:55-61`) is the one place that already invalidates `["pr-runs", prId]` and `["pr-intent", prId]` for exactly this reason (a finished run changes derived per-PR state). Adding the Smart Diff feature's `["smart-diff", prId]` cache followed the same rule: invalidated inside `invalidateRunHistory` (the finished-run signal); the extra invalidation in `useRunReview.onSuccess` only mirrors the existing `["reviews", prId]` one and is not what refreshes the indicators. Any future feature that derives UI state from "the latest finished review" should invalidate its query key in `invalidateRunHistory`, not in the run-trigger mutation's `onSuccess`.

## 2026-09-27 — [Context] `@devdigest/ui`'s `MonoLink` has no `aria-label` passthrough — a link needing a custom accessible name must be a local `<a>`, not `MonoLink`
`vendor/ui/primitives/MonoLink.tsx` destructures only `children`/`onClick`/`href` (no prop spread), so it cannot carry an `aria-label` distinct from its visible text. The Blast Radius card's caller links (`BlastSymbolRow.tsx`) need an accessible name from the `callerLinkLabel` translation ("Open {file} line {line} on GitHub"), not the raw `file:line` text shown to sighted users (R7) — reusing `MonoLink` as originally planned would silently drop that translation. Rendered a local `<a className="mono" target="_blank" rel="noopener noreferrer" aria-label={...}>` instead, matching `MonoLink`'s visual styling without needing to widen its prop API (which is out of scope for a feature-owned file). Any future caller-link-with-custom-label need should do the same rather than editing `MonoLink` from inside a feature task.

## 2026-09-27 — [Mistake] A `useState` lazy initializer can't capture "the first item from a TanStack Query result" — the query's `data` is `undefined` on the very first (loading) render
`BlastRadiusCard`'s original attempt at "the first downstream row starts expanded" (R11) used `useState<Set<string>>(() => new Set([data?.downstream[0]?.symbol]))` — but `useState`'s lazy initializer only runs once, on mount, and `usePrBlast(prId)`'s `data` is still `undefined` on that first render (before the query resolves), so the captured default was always an empty set regardless of what loaded afterward. Fixed by storing `Set<string> | null` (`null` = "user hasn't toggled anything yet") and computing the actual default (`index === 0`) inline at render time from `data.downstream`, falling back to the stored `Set` only once the user interacts — avoids both the stale-initializer bug and an `useEffect`-to-sync-derived-state anti-pattern. Any "default the first N items of an async list to some UI state" feature built on `useState`'s initializer function should be treated as suspect if the data source is a query/fetch, not a prop already available synchronously on mount.

## 2026-09-27 — [Mistake] A "record the current status as baseline, then poll until it changes" pattern silently never terminates when the status isn't loaded yet at click time
`useBlastResync.ts`'s `start()` (T8) originally did `baselineRef.current = status ? {...} : null`, then the sync effect only ever compared against `baselineRef.current` and no-opped when it was `null` — so if `useRepoIntelStatus`'s query hadn't resolved yet the instant the Resync button was clicked (a real race, not an edge case: the status query and the button are both available as soon as the card mounts), the effect could never detect "advanced" and the poll ran for the full `RESYNC_POLL_MAX_MS` (130s) every time, even though the underlying resync usually finishes in seconds. Fixed with a second ref, `baselinePendingRef`: when `start()` finds no status yet, it sets `baselinePendingRef.current = true` instead of leaving a permanent `null`; the polling effect's first invocation with pending set just *captures* that status as the baseline (not a fresh no-op skip) and only compares subsequent statuses against it. General lesson: a "diff against a baseline captured at click time" pattern needs an explicit fallback path for "no baseline was available yet" — silently treating it as "never advanced" turns a fast operation into a worst-case-duration one, and unit tests that always seed the status before clicking won't catch it.

## 2026-09-27 — [Mistake] `useBlastResync`'s original `start()` silently swallowed a failed resync — the fix also needs `setPolling(true)` to run BEFORE `mutate()`, not after
The Resync button (T8) originally called `resync.mutate()` with no `onError`, so a failed `POST /repos/:id/resync` (a 202-body-shaped "degraded" response, or — after the matching server fix, see server Insights 2026-09-27 — a real 404/409) left the button spinning until `RESYNC_POLL_MAX_MS` (130s), then just stopped with no explanation. Fixing this by passing `mutate(undefined, { onError: … setPolling(false) … })` initially looked sufficient but broke under a synchronous test mock (and is a latent risk with any mutate implementation that can settle synchronously): the original code ran `resync.mutate(...)` THEN `setPolling(true)`, so if `onError` fires before `mutate()` returns, its `setPolling(false)` gets immediately clobbered by the `setPolling(true)` on the next line — the UI ends up "running" even though the request already failed. Fixed by moving `setPolling(true)` (and arming the timeout) to BEFORE calling `resync.mutate(...)`, so `onError`'s `setPolling(false)` is always the last write regardless of how synchronously the mutation settles. General lesson: when a callback passed into a fire-and-forget call (`mutate(vars, { onError })`) can update the same state a line right after the call also updates, order the "optimistic" state update before the call, not after — otherwise a same-tick callback silently loses the race.
